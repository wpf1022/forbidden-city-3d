## 一、总评

架构是站得住的：屋顶高度场把"平面线性收分 + 立面非线性举折"解耦，四个坡面与四条垂脊共用同一套角部位移公式，所以翼角天然不开缝；昼夜是一份状态对象整体插值，两张 PMREM 预烘，不存在过渡态缺贴图；合并与实例化是真在省 draw call；引导守卫把 `file://` 这个最容易劝退人的坑挡在模块之外。

问题集中在**"代码里写了，但屏幕上没有"**这一类：踏跺被埋进台体、檐下被背面剔除、贴图的 UV 尺度体系整体失效、正脊与垂脊绕序朝内。它们有一个共同点——**从默认预设视角看不出来**，所以视觉迭代没抓到，只有逐行读几何生成代码才会暴露。

这也说明一件事：**我用截图验收的方式，只能验收"我选的那几个角度"**。三张预览图都成立，不代表场景成立。

## 二、P0 必修（5 项）

### P0-1　檐下整片被背面剔除，抬头能看穿屋顶
`src/architecture/roof.js:136-148`，材质 `src/materials.js:34-38`（默认 `FrontSide`）

`makeShell()` 生成下壳时**复用了顶面的索引绕序**，只把法线取反了（147-148 行）。绕序意味着正面朝向：顶面朝上，下壳也朝上 → 从下方看是背面 → 被剔除。

后果：`soffit` 材质与整块下壳几何是白做的。相机贴到 y≈2.2（`config.js:69` 的 `minY`）、距建筑 25 m 时抬头，直接看到天空或背景。双壳厚度在视觉上只剩一圈檐口封边。

**修**：`under` 的索引整组反序（`computeVertexNormals` 会自然朝下），删除 147-148 的法线取反。不要用 `BackSide` 绕过去——那样从上方看又会被它的背面挡住。

### P0-2　六座台基没有一条可见踏跺，御道断在台壁上
`src/architecture/platform.js:77-99` + `:187`

台阶局部坐标是 `z = -(i+1)*tread + tread/2`，即**沿 -z 向台体内部逐级升高**；`stairsGeometry` 的御路斜板也在 `-run/2`。然后 `translate` 只加了半个进深，没加 `run` → 整条踏跺连同御路、两侧石栏全部埋在实心台体内，且最高一步在最深处。

**已验证**：`docs/preview/03-central-axis.jpg` 与 05 号图里，三层台基南面没有任何投影台阶，白色御道走到台前直接消失。`stairs` 这个参数与 README 第 198 行"踏跺御路"的承诺同时落空。

**修**：`run = n*tread`；`translate` 改为 `halfD + run + 0.02`；多层台基第 i 层的起坡高度改为 `i*tierH`、起点放在外层台缘，否则补上 run 之后会穿进下一层台体。附带：栏板需在踏跺处开口（`balustradeMatrices` 按 `|x| < stairs/2` 跳过若干跨）。

### P0-3　最近距离处相机进入建筑体，FR-3D-02 的验收条目未实现
`src/render/controls.js:119-125`（只钳 radius）、`:181-190`（只钳 y）、`src/config.js:69/83`

PRD 的验收标准原文是"缩放到最近时不穿入建筑内部"。实测：预设 a 的 target `(2, 21, -50)` **本身就在太和殿屋顶体积内**；取合法的 `phi=1.5`、`radius=25`，机位落在 `(19.4, 22.8, -32.2)`——上层殿身墙盒内部。所有建筑材质都是 `FrontSide`，进体后整面被剔除，建筑"消失"。

台基高 8.1 m 而 `minY` 只有 2.2 m，台基体积同样中招。

**修**：给六处建筑与台基一份 keep-out AABB，在 `_applyCamera` 里沿视线把半径二分外推到盒外；同时把预设 target 移出建筑体。

### P0-4　可见天空绕过色调映射：天空不吃曝光，雾色与地平线对不上
`src/render/sky.js:126`（`toneMapped: false`）+ `:97-99`（手动 include）

three 在 `toneMapped: false` 时把 `parameters.toneMapping` 置为 `NoToneMapping`，于是 `TONE_MAPPING` 宏不存在，而 `<tonemapping_fragment>` 整个函数体被 `#if defined( TONE_MAPPING )` 包住 —— **`sky.js:98` 那行是死代码**。

**已验证**（像素级）：把 `renderer.toneMappingExposure` 从 0.95 改到 0.2，天空像素完全不变（`(136,163,194) (141,168,196) (146,168,189)` 逐点相同）；同一帧里地面与建筑明显变暗。天空既不参与 ACES 也不吃曝光。

后果：`lighting.js:29/32` 特意把 `fogColor` 与 `skyHorizon` 设成同一个 `0x93aec8`，但完全雾化的地面走 ACES、天空不走，屏幕上在地平线处留下一条亮带。

**修**：`toneMapped: true`，**并保留** `#include <tonemapping_fragment>`。
⚠️ 这里我与评审席②的结论不一致：他们建议"删掉手动 include，three 会自动注入"——**对 `ShaderMaterial` 不成立**。three 只自动注入 `<tonemapping_pars_fragment>` 与 `toneMapping()` 函数，**调用**必须由着色器自己 include。我实测按他们的方案改（删 include + 翻 flag）后天空像素与改前一致，等于没修。正确的最小改动是**只翻 flag**，实测地平线亮带基本消失。

### P0-5　`≤300 draw call` 的验收数字漏算了阴影 pass，真实值 366
`src/main.js:150`、`README.md:141/252`

three r170 的 `render()` 是**先 `shadowMap.render()`、后 `info.reset()`**，所以 `renderer.info.render.calls` 只统计主 pass。

**已验证**（运行时实测，`info.autoReset=false` + 手动 reset）：

| 场景 | 主 pass | 含阴影 pass |
|---|---|---|
| 默认视角（a） | 157 | **366** |
| 高空全景（c） | 约 276 | 超 400 |

阴影 pass 单独就是 209 次。PRD 的单帧上限是 300，**已超**。README 与 `tools/verify.js` 公布的 176/276 都是半张账单。

**修**：先把度量改对（`autoReset=false`，每帧 render 前手动 `reset()`）；再真正降：25 段宫墙（50 个 mesh）与 4 条廊庑按材质合并，单项即可砍掉 60+ 次。

## 四、P2 可选（合并同类，共 14 项）

**正确性**：法线图 G 通道符号反（`textures/index.js:62-68`，`flipY` 导致应为 `+dy`）；`?v=constructor` 命中原型链导致停在加载层（`main.js:90`）；帧循环无 try/catch，一次异常永久冻结（`main.js:128`）；`alongRect` 少填一个角（`geom.js:176-198`，当前未被使用）。
